# 设计文档：为什么这么做

只讲**为什么这么选、替代方案是什么、代价在哪**。代码做什么，读代码就知道。

---

## 0. 要回答的问题

> 一个能跑长任务的 Agent 运行时，**必须**具备哪些机制？缺了哪个会崩？

这个项目不是"再做一个多智能体 demo"，而是把这个问题拆开、逐个实现、逐个验证。
所以每个模块的存在理由，都对应一类**具体的失败**：

| 机制 | 不做会怎样 |
|---|---|
| 任务清单 + 依赖图 | 模型做完第一步就以为做完了；或跳步执行（没核实政策就先设计组合） |
| 子 Agent 委派 | 主上下文被原始材料淹没，二十轮后撞上下文上限 |
| 上下文压缩 | 同上，且即使没撞上限，"中间遗忘"会让模型忽略关键信息 |
| 分层记忆 | 同样的坑每次都踩，跨会话经验无法复用 |
| 权限与审计 | Agent 能读写任意路径；出问题查不到是谁改的 |
| 链路追踪 | 答案错了，无法判断是"检索没找对"还是"模型没用检索结果" |
| 目标闭环 | 模型完成任务一半就收工，且自认为完成了 |

---

## 1. 为什么手写运行时，而不用 LangGraph

面试必被问："你用框架还是自己写的？为什么？"

框架能替你做掉的事，恰好是本项目要交付的能力：
主循环怎么组织、上下文压缩什么时候触发、Hook 挂在哪个节点、中断后怎么恢复。

具体到本项目，有三处框架的抽象会挡路：

1. **压缩触发时机**。压缩太早浪费 token 做摘要，太晚撞上限。
   本项目要在 `before_model` 节点拿到真实的消息数组做判断，
   而框架通常把消息管理封装在内部，外部只能给个"最大 token 数"。
2. **工具结果的落盘决策**。本项目要把超长结果写进虚拟文件系统、
   上下文只留摘要和路径。这需要在 `after_tool` 节点改写结果。
3. **子 Agent 的权限收窄**。复核员刻意不给写权限（避免"自己改自己验"），
   这要求工具池按角色动态组装。

替代方案与代价：手写意味着要自己处理消息格式、tool_call 的配对约束、
重试与限流。本项目为此写了约 200 行 `llm.py`——
**换来的是对全链路的完全控制**，这个交换是划算的。

## 2. 主循环：能力用中间件扩展

`loop.py` 里没有一处 `if 开启了记忆就...`。所有机制都挂在四个节点上：

```
before_model   ──►  模型调用  ──►  after_model
                                     │
before_tool    ──►  工具执行  ──►  after_tool
                                     │
before_finish  ──►  返回
```

**为什么这个结构重要**：扩展不改主循环。加审计、加限流、加敏感信息过滤，
都只挂 Hook。主循环永远只有一件事——推进对话。

代价：调试时调用链更深（一个工具调用要经过 Hook 链才知道最终参数）。
所以 Hook 执行本身有耗时记录（`HookManager.stats`），出问题能定位到具体 Hook。

---

## 3. 子 Agent：核心是上下文隔离，不是"多几个 Agent"

**机制**：主 Agent 用 `task` 工具发起委派，子 Agent 在自己的上下文里跑完，
主 Agent 只收到结论字符串。

**为什么值**：子 Agent 可能翻 20 页政策原文、试 16 种资产组合；
这些原始材料**一行都不会进主上下文**。主上下文只多了一条几百字的结论。

**代价必须说清楚**：子 Agent 看不到主对话历史。所以委派时，
必要背景必须写进 `goal`。这不是缺陷——写不清楚 goal，
说明任务边界本身没定义好，这恰恰是应该被暴露出来的问题。

**权限收窄**：三个角色的工具集不同。
- `policy_researcher`：只能查政策（检索 + 政策库 + 读文件）
- `tax_calculator`：只能算（算例 + 测算 + 优化）
- `verifier`：**刻意不给写权限**——复核员能改材料，复核就没有意义了

## 4. 上下文压缩：必须做，且边界不能切错

两条策略：

1. **溢出落盘**：单条工具结果超过 2000 字符 → 写进 `workspace/artifacts/`，
   上下文里留「前 400 字 + 完整路径」。**压缩不等于丢失**——
   后续 Agent 可以 `read_file` 取回，也可以委派子 Agent 处理。
2. **历史蒸馏**：整段对话超过预算 → 把最早的一批消息压成一条摘要，
   保留最近 8 条原文。

### 一个必须记住的坑：裁剪点不能乱切

OpenAI 兼容格式要求：`assistant` 消息里的 `tool_calls`，必须被紧随其后的
`tool` 结果消息一一回应（靠 `tool_call_id` 匹配）。**从中间切开，下次请求直接 400。**

所以裁剪点只能落在两类边界上：
- `user` 消息（一轮新输入的开始）
- 带 `tool_calls` 的 `assistant` 消息（一次调用组的开头）

只找 `user` 是不够的：像"一次提问触发二十轮工具调用"这种长任务，
整段对话只有一个 `user`，只认 `user` 就永远压不动。
**这个 bug 是被单元测试抓出来的**（`tests/test_context.py::test_compact_works_when_only_one_user_turn`）。

## 5. 记忆：不是"做了个向量检索就叫记忆"

三层：短期（对话消息）/ 工作（本次任务笔记）/ 长期（跨任务沉淀，落盘）。

长期记忆实现了三个机制，少了任一个，"记忆"就只是个越写越大的文件：

| 机制 | 作用 | 不做会怎样 |
|---|---|---|
| **衰减** | 半衰期 14 天，久未使用的权重下降 | 三年前的旧经验一直和昨天的新经验等权 |
| **强化** | 被召回并命中一次，权重上升 | 真正好用的经验淹没在噪声里 |
| **淘汰** | 权重低于阈值且从未用过 → 删除 | 记忆库无限膨胀，检索越来越慢越来越差 |

**检索方式的选择**：用「关键词重合 × 衰减 × 强化」打分，不是向量检索。
理由是规模——经验条目几十到几百条，词面信号足够，不值得为它多付一次
embedding API 调用。**上千条之后换向量检索更合适**。这是规模决定方案，
不是"哪种技术更高级"。

## 6. Skills：渐进披露省的是上下文预算

一个 Skill = 一个目录 + `SKILL.md`（frontmatter 描述 + 正文）。

三层加载：
1. system prompt 里只放 `名称：一句话描述`（约 20 字/个）
2. 模型判断需要时 `load_skill(name)` 取正文
3. 正文引用的参考文件，再按需 `read_file`

**对比"把所有流程写进 system prompt"**：那样每个任务都被无关 SOP 干扰，
且改一条要动整个提示词。Skills 让流程变成按需加载的模块——
挂 30 个技能的成本是 30 行 prompt。

本项目挂了 3 个技能：政策时效核查、筹划方案设计、结论报告撰写。

---

## 7. Workflow：确定性编排与一条安全红线

固定流程（核查 → 测算 → 复核）写进脚本，模型只给名字和参数。

**安全红线：模型不能提交可执行代码。**
模型能给的只有 workflow 名、参数字典、可选的续跑 run_id。
否则这就是一个远程代码执行漏洞——这是 MCP / Workflow 这类"让模型触发宿主能力"
的设计里最容易踩的坑。

**journal 续跑**：每步结果落盘。跑到一半断了（超时、限额、人工中断），
带 run_id 重启时已完成步骤直接复用，不重复烧钱。
返回结果里区分 `executed` 与 `reused_from_journal`，续跑省了多少一目了然。

## 8. Goal Loop：为什么"模型说完成"不算数

主循环原本的退出条件：模型不再调工具 → 返回。
对"给出可复核的筹划方案"这种任务，这远远不够——模型可能做了一半就认为完成了。

本项目做了**两级判断，先便宜后昂贵**：

1. **确定性**（零成本）：任务清单还有未完成项 → 不许收工。
   这一级能挡掉大部分情况，而且完全不依赖模型判断。
2. **模型判定**（一次额外调用）：条件本身是开放式时（如"节税额测算完成且有依据"），
   交给一个独立判断器。提示词明确要求**宁可判未完成，也不要放过半成品**。

兜底：最多续跑 3 轮，避免无限循环。达到上限时把缺口写进工作记忆，如实收工。

## 9. 检索层：为什么自实现而不用向量库

先说过程：最初用 Chroma，其 Rust 绑定在建大集合时报 `Error loading hnsw index`
（81 条正常，2909 条必崩），跨进程重新打开时暴露，预计算向量、调大写入批次都没用。

于是做量化评估：

| 方案 | 单次查询 | 依赖风险 |
|---|---|---|
| 向量库（HNSW / IVF 近似检索） | 微秒级 | 有 |
| numpy 精确检索 | **0.26 ms**（2909×1024） | 无 |

一次 embedding API 调用要几百毫秒——**检索耗时比它低三个数量级**。
近似索引省下的时间根本看不见，而引入一个会损坏、要额外安装的依赖是纯负收益。

**收敛**：规模到十万级片段再换 FAISS/Milvus 不迟，`VectorStore` 的接口就是为此留的。

## 10. 已知局限（主动写出来）

1. **只在税筹域验证过**。机制的通用性需要换域再验一次。
2. **s11 后台任务、s12 cron 调度没做**。本域没有真实需求，硬塞只会多两个讲不清的模块。
3. **MCP 是进程内模拟**，不是真实 stdio/HTTP transport——那部分是协议实现，不是 Agent 能力。
4. **子 Agent 之间不能通信**，只有主 Agent 收结论。真正需要协商的场景（两个子 Agent 结论冲突）未覆盖。
5. **记忆检索用词面匹配**，经验条目上千条后需要换向量检索。
6. **成本未做预算控制**：没有令牌桶限流，长任务可能超支。
