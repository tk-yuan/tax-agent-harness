# 术语速查：简历上每个词都要能答

按「是什么 → 为什么用它 → 面试怎么答」三段写。**答不出"为什么"就别往简历上放。**

---

## 一、服务与接口

### ASGI
Python 的**异步服务网关接口**标准，WSGI 的继任者。

| | WSGI（老） | ASGI（新） |
|---|---|---|
| 模型 | 同步，一请求占一线程 | 异步，支持并发 |
| 长连接 | 不支持 | 支持 WebSocket / SSE |
| 代表 | Flask + gunicorn | FastAPI + uvicorn |

**为什么本项目用它**：要把 Agent 执行过程用 SSE 实时推给前端。一次任务几十秒到几分钟，
用 WSGI 这条连接会把 worker 占死，两个并发就卡住。

> **面试答**：ASGI 是 Python 的异步网关接口标准，相比 WSGI 支持长连接和并发。
> 我用它是因为要用 SSE 把 Agent 执行过程实时推给前端，任务是分钟级的，
> WSGI 的同步 worker 会被占死。

### SSE（Server-Sent Events）
服务端**单向**往浏览器推事件的长连接，基于普通 HTTP。

**为什么不用 WebSocket**：执行事件是单向的（服务端→浏览器），不需要双向。
SSE 更简单、能自动重连、走普通 HTTP，不用引入额外协议。

### FastAPI
基于 ASGI 的 Python Web 框架，自带 Pydantic 校验与自动文档。

**为什么用它**：类型校验 + 自动生成 `/docs` 接口文档，写 API 省事且不易写错参数。

## 二、检索

### 嵌入（Embedding）与 bge-m3
**嵌入 = 把文本变成一串数字（向量）**，这样"语义相近"可以用数学比出来。

`bge-m3`：BAAI（北京智源研究院）出的多语言嵌入模型，输出 **1024 维**向量。
m3 = 多语言 / 多功能 / 多粒度。中文检索的主流选择。

> **面试答**：嵌入模型把文本编码成向量，语义相近的向量距离就近。
> bge-m3 是智源的多语言模型，1024 维，中文政策文本上它是当前的主流选择。

### 重排（Rerank）与 bge-reranker-v2-m3
**两种范式，必须能说清区别**：

| | 双塔（嵌入/向量检索） | 交叉编码（重排） |
|---|---|---|
| 做法 | query 和文档**各**编码一个向量，比距离 | query 和文档**拼在一起**过一遍模型 |
| 速度 | 快（可预计算） | 慢（每条都要现算） |
| 精度 | 粗 | 准 |

**标准用法**：向量召回一大批（top-20）→ 重排精挑（top-3）。这叫「召回 + 精排两段式」。

> **面试答**：嵌入是双塔，各自编码一次算相似度；重排是交叉编码，拼起来算相关性。
> 所以先向量召回一大把，再用重排精排。我的消融验证过——重排把 Recall@3 提了，
> 但也拉低了 Recall@1，是取舍不是必然更好。

### BM25
经典**关键词**检索算法（Okapi 公式），按词频和文档频率打分。

**为什么还要它**：向量检索擅长语义相近（"小微企业"↔"小型微利企业"），
但文号、数字这类**必须精确命中**的信号会被糊掉；BM25 正好相反。

### RRF（Reciprocal Rank Fusion）
**把多路检索结果合成一路**的方法：`score(d) = Σ 1/(k + rank_r(d))`，k 通常取 60。

**为什么不用加权求和**：向量分是余弦相似度（0~1），BM25 分是无界实数，
**量纲不同**，加权需要调一个没有理论依据的系数。RRF 只看名次，天然规避。

### 切分策略（Chunking）
把长文档切成检索单元。本项目对比三种：
- `fixed`：固定长度切
- `recursive`：按段落/句子逐级切（LangChain 默认思路）
- `article`：**按政策条款边界切**（「一、」「二、」）——领域感知

### 评测指标
| 指标 | 含义 |
|---|---|
| Recall@k | 前 k 条里命中金标的比例 |
| MRR | 第一个命中项的排名倒数（排得越前越高） |
| nDCG@k | 考虑位置折损的累积增益 |
| P@k | 前 k 条里相关文档占比（衡量噪声） |

**一个必须能讲的细节**：先截断 top-k 再去重，不是先去重再截断。
同一份政策占两个名额意味着挤掉了另一份可能的答案，这个代价必须体现。

### 消融实验（Ablation）
**控制变量法**：一次只改一个因素，看指标怎么变，从而归因。
本项目 7 组：3 种切分 × 3 种检索 × 有无重排。

**为什么重要**：不做消融，你就只知道"我用了混合检索"，不知道为什么、值不值。

## 三、Agent 运行时

### Agent Harness
**Agent 的运行时外壳**——不是 Agent 本身，而是让它能跑起来的那一层：
主循环、工具分发、上下文管理、权限、状态持久化。

**为什么手写不用 LangGraph**：本项目要交付的就是这一层，
而框架恰恰把它替你做掉了。**框架能做的部分，就是我要证明我会做的部分。**

### 工具调用 / Function Calling
把函数签名和描述给模型，模型决定调哪个、传什么参数。

### 子 Agent 委派
主 Agent 把可独立的子任务交给子 Agent，**只收回结论**。

**核心价值是上下文隔离**：子 Agent 翻 20 页原文、试 16 种组合，
这些原始材料一行都不进主上下文。

**代价**：子 Agent 看不到主对话历史，委派时必须把背景写进 goal。

### 上下文压缩（Compaction）
两条策略：
1. **溢出落盘**：单条工具结果超长 → 写文件，上下文只留摘要 + 路径
2. **历史蒸馏**：对话过长 → 最早一批消息压成摘要

**必须能讲的坑**：压缩的裁剪点只能落在 `user` 消息或带 `tool_calls` 的 `assistant` 消息上。
从别处切会把 tool_calls 和 tool 结果拆散，下次请求 API 直接 400。
而且**只找 user 是不够的**——"一次提问触发二十轮工具调用"的长任务整段只有一个 user，
只认 user 就永远压不动。

### 四节点 Hook / 可插拔中间件
在模型调用、工具调用、文件读写、任务状态变更四个节点注入扩展点。

**为什么这么设计**：扩展不该改主循环。加审计、加限流、加审批，都只挂 Hook。

### Skills 渐进披露
技能按三层加载：**目录（名字+一句话）→ 正文 → 引用的参考文件**。

**为什么**：挂 30 个技能的成本是 30 行 prompt，而不是 30 份完整 SOP 塞进上下文。

### 分层记忆与衰减
短期（对话）/ 工作（本次笔记）/ 长期（跨任务落盘）。
长期层实现**衰减**（半衰期 14 天）、**强化**（召回命中加分）、**淘汰**（权重过低删除）。

**为什么必须有这三个**：只有存储不叫记忆。没有衰减，三年前的旧经验和昨天的等权；
没有淘汰，记忆库无限膨胀、检索越来越差。

### 人工审批门（Human-in-the-loop）
高风险操作**阻塞等人批复**，超时自动拒绝。

**为什么阻塞而不是异步**：有对外后果的动作不能"先做了再补审批"，
否则审批只是事后通知，约束不了任何东西。

### 目标闭环（Goal Loop）
模型说"完成了"不算数，另起一次**独立判断**（零成本的确定性检查 + 有成本时的模型判定）。

**为什么**：Agent 常见失败模式是做了一半就自认为完成。

### 执行链路追踪（Trace）
一次任务一个 trace_id，每步一个 span，记录输入输出、耗时、token。
产出 JSON（可程序化断言）+ HTML（人看的时间线）。

**为什么需要**：Agent 是概率系统。答案错了，没有 span 级记录，
根本判断不出是"检索没找对"还是"模型没用检索结果"。

## 四、被问到时最该说的三句

1. **"为什么不用框架？"** → 我要控制上下文压缩的触发时机、Hook 注入点、子 Agent 权限边界和中断恢复，这些恰好是框架替我决定的部分。

2. **"重排一定更好吗？"** → 不一定。我的消融显示它提升 Recall@3 但拉低 Recall@1，是取舍。下游读 top-3 就用，只读 top-1 就别用。

3. **"怎么保证合规？"** → 三层：工具级路径白名单、Hook 级权限与审计、状态级任务依赖约束；有对外后果的动作走阻塞式人工审批。
