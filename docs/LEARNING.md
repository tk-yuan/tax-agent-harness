# 学习指南：怎么把这套东西讲出来

面试官不会问"你用了什么框架"，会问"为什么"。这份文档按**问题**组织，
每条给出本项目的答案、以及追问会往哪走。

先记住一句话总结：

> 我手写了一个 Agent 运行时，因为我要控制上下文压缩的触发时机、Hook 的注入点、
> 子 Agent 的权限边界和中断恢复——这些恰好是框架替我做掉的部分。

---

## 一、Agent 基础

**Q：Agent 和直接调 LLM 有什么区别？**

直接调 LLM 是「一问一答」。Agent 是「给定目标，自行决定调哪些工具、调几轮、
什么时候停」。本项目的差别体现在 `runtime/loop.py`：主循环带着工具池反复问模型，
直到模型不再请求工具、且通过收工检查。

**Q：Agent 和 Workflow 有什么区别？为什么两个都要？**

Workflow 的步骤顺序**执行前已知**；Agent 的下一步**取决于上一步的发现**。

本项目两个都有：`plugins/workflow.py` 处理「核查 → 测算 → 复核」这类固定流程
（顺序写死在脚本里，模型只给参数）；主循环处理开放任务。
固定流程硬套 Agent 会更慢更不稳，开放任务硬套 Workflow 会做不了。

**Q：你的 Agent 怎么保证每一步是合法的？**

三层：工具级（`permissions.py` 的路径白名单与工具分级）、Hook 级
（`before_tool` 的权限校验与审计）、状态级（任务依赖图——前置未完成不能开工）。

## 二、上下文工程（高频追问区）

**Q：长任务上下文爆了怎么办？**

两条策略（`context/compaction.py`）：

1. 单条工具结果 > 2000 字符 → 落盘到 `workspace/artifacts/`，
   上下文只留「前 400 字 + 文件路径」。**压缩不等于丢失**，后续可 `read_file` 取回。
2. 整段对话超预算 → 最早的一批消息蒸馏成一条摘要，保留最近 8 条原文。

**Q（追问）：从中间切消息不会有问题吗？**

会。OpenAI 兼容格式要求 `assistant.tool_calls` 必须被紧随其后的 `tool` 结果
一一回应，从中间切开下次请求直接 400。所以裁剪点只落在组边界上：
`user` 消息，或带 `tool_calls` 的 `assistant` 消息。

**Q（追问）：只找 user 不就行了吗？**

不行。「一次提问触发二十轮工具调用」这种任务整段只有一个 user，
只认 user 就永远压不动。**这个 bug 是单元测试抓出来的。**

**Q：什么是 lost in the middle？**

长上下文中，模型对首尾信息的利用明显好于中间。所以压缩不是单纯为了省 token，
也是为了让关键信息不被淹没在中间。

## 三、记忆系统

**Q：你的"长期记忆"具体是什么？**

三层：短期（对话消息）、工作（本次任务笔记）、长期（跨任务沉淀，落盘 JSONL）。

**Q（追问）：那不就是存个文件吗？**

只有存储不叫记忆。本项目实现了三个机制：

- **衰减**：半衰期 14 天。久未使用的经验权重下降，否则三年前的旧经验和昨天的等权。
- **强化**：被召回命中一次，权重上升。好用的经验才会浮现。
- **淘汰**：权重低于阈值且从未用过就删除，否则记忆库无限膨胀、检索越来越差。

**Q（追问）：为什么不用向量检索？**

规模决定的。经验条目几十到几百条，词面信号足够，
不值得为它多付一次 embedding API 调用。**上千条之后换向量检索更合适。**

这个回答本身是加分点——说明是按规模选方案，不是按技术热度选。

## 四、多智能体

**Q：子 Agent 的价值是什么？**

**上下文隔离。** 子 Agent 翻 20 页政策原文、试 16 种组合，
这些原始材料一行都不进主上下文，主 Agent 只收到几百字结论。

**Q（追问）：子 Agent 看不到主对话历史，怎么保证它能干活？**

委派时必须把背景写进 `goal`。这不是缺陷——写不清楚 goal，
说明任务边界没定义好，这正是应该暴露的问题。

**Q（追问）：怎么防止两个子 Agent 结论冲突？**

本项目只做了单层委派，主 Agent 收结论后自行判断。
真正需要协商的场景（子 Agent 之间对话）没做——**这是局限，我写在文档里了**。
诚实地承认没做的部分，比硬说有更强。

**Q：为什么复核员不给写权限？**

避免「自己改自己验」。这是权限收窄的一个具体例子：
`SubagentSpec.allow` 按角色给最小工具集。

## 五、可靠性

**Q：工具调用失败怎么办？**

`loop.py` 里工具异常被捕获后作为**工具错误**返回给模型，
而不是中断整个任务——模型可以换个方式再试。Hook 层则相反：
`before_*` 的 Hook 出错必须**拒绝**（不能悄悄放行），`after_*` 出错不影响主流程。
这个不对称是刻意的。

**Q：模型调用失败呢？**

`llm.py` 做 3 次指数退避重试；仍失败则返回 `stop_reason="model_error"` 并如实上报。

**Q：怎么防止 Agent 死循环？**

三重：`max_turns` 限制单次任务轮数；Goal Loop 最多续跑 3 轮；
Workflow 的步骤由脚本固定，不存在模型自己绕圈的可能。

**Q：怎么防止模型提交恶意代码？**

Workflow 只接受**流程名 + 参数 + 续跑 id**，不接受可执行代码——
脚本由宿主注册。否则就是个远程代码执行漏洞。
MCP 外部工具默认按**非只读**处理（外部来源不可默认可信）。

## 六、可观测性

**Q：Agent 出错了怎么定位？**

`observability/trace.py`：一次任务一个 trace_id，每步一个 span，
记录输入输出、耗时、token。产出两份——`.json` 可程序化断言（做回归测试用），
`.html` 是人类可读时间线。

**Q（追问）：为什么要有 JSON 版？**

因为要对它做**断言**。"每次任务都必须调用过 optimize_plan"
"合规校验必须返回 compliant=true"——这类断言可以做成回归测试，
防止改动让 Agent 悄悄退化。这是从"能跑"到"可维护"的关键一步。

## 七、可能会被问倒的地方

1. **s11 后台任务、s12 cron 调度为什么没做？**
   答：本域没有真实需求。硬塞只会多两个讲不清的模块。
   如果要做，政策库的时效巡检是个自然的落点——这正好接上毕设里
   "政策有效期未被纳入优化模型"那个缺口。

2. **MCP 是真的吗？**
   答：进程内模拟 server，演示 tools/list 与 tools/call 和动态工具池。
   真实 stdio/HTTP transport 没实现——那是协议实现，不是 Agent 能力。

3. **成本控制了吗？**
   答：**没有做限流**，长任务可能超支。这是已知局限。

---

## 八、最该记住的三个"反直觉点"

1. **压缩的裁剪点不能乱切**——组边界，且只找 user 会压不动。
2. **记忆不是存储，是衰减 + 强化 + 淘汰**。
3. **检索不一定要用向量数据库**——0.26ms 的暴力检索比 embed 一次快三个数量级。
